# Council: make the plugin an easy workflow, with optional steps

*2026-10-22. Chaired by the CTO agent. Proposed decision in [ADR-0003](../adr/0003-simple-default-path.md).*

The founder asked the council to review what is in the repo now, without adding process, so that the workflow is easy to go through and most steps are optional. Seven experts each walked a small feature (a saved-items list) and a bug through the plugin: product owner, tech lead, QA, architect, SRE, project manager and agentic AI.

## What they measured

| | Feature (light lane today) | Bug |
|---|---|---|
| Documents before the PR | 8 to 11 | 1 (plus the review ledger) |
| Required sections | about 50 | 8 |
| Human waits | 5 (6 in the full lane) | 1 |
| Commands (slash plus `sdlc`) | about 8 plus 15 | about 9 |
| Concepts to learn first | about 25 | a few |

All seven said the same thing: **the bug lane is about right; features are far too heavy.** Every feature starts in the full lane and waits two 24-hour gates before it can be made light (project manager, architect).

## Where they agreed

| Point | Who | Result |
|---|---|---|
| Build passes on checks in every lane, as bug and task already do; the human Build gate is a sign-off on what the gate already proves | tech lead, project manager | Adopted |
| `sdlc advance` folds into `approve` and into a check-passed `request` | tech lead, project manager | Adopted |
| Features default to the light lane; full only for data changes that alter or drop, high-risk paths or a new component | project manager, architect, agentic AI | Adopted |
| One spec document for Plan and Analyze: a short PRD plus `acceptance.feature`, one human approval | product owner, tech lead, agentic AI, project manager | Adopted |
| The test proof is the one check that a test can fail; the Mutations table, "mutation-test every guard" and "show each test failing" prose duplicate it | QA, tech lead | Adopted: the prose and table go |
| Level enforcement in the test matrix and the Gherkin style lint fail good tests; keep only the AC and R tags as errors | QA | Adopted: style becomes warnings |
| Duplicated sections: spec Requirements and Acceptance criteria copy the PRD and the feature file; Test strategy, Test data and the "How it fails" table say the same thing | product owner, QA, architect | Adopted: one `## Test plan` |
| The design board runs only when there is an ADR or a high-risk path; no board on the `## Plan` fallback | architect, project manager | Adopted |
| The safety core stays (below) | all seven | Adopted |
| Fewer agents and commands; one skill; one knowledge base | agentic AI | Adopted |

## The safety core (mandatory, every lane)

1. Only a human approves a gate, declares a hotfix, merges or deploys. Hooks refuse agents; the GitHub ruleset enforces merges.
2. The gate command is green and at or above the baseline.
3. The test proof for features; a repro test that fails first for bugs, proved on the base code, not "any red run" (QA found `reproRedAt` accepts any red gate).
4. A pre-review with `Risk:`, `Look here first:` and no open blocker or major; then a CODEOWNER review.
5. The PR line limit.
6. Release: a tested rollback, probe results and a human approval.
7. Schema changes detected; breaking API changes declared.
8. The kill switch, the secret scans, no production data in tests, the retry cap.

## The contested points, and how the CTO settled them

**C1. Do the "remember" checks block Release?** ADR-0002 made stale knowledge, stale facts, unmarked superseded ADRs and unlinked postmortem actions block Release. The SRE called it bookkeeping on the release path; the product owner and architect value it.
- *Settled:* they become **warnings** at Release and a list in `status`, not blocks. The release checks that block are the three that protect production: tested rollback, probe results, human approval. This amends ADR-0002.

**C2. Earned trust: cut or keep?** The project manager wants it cut: once Build passes on checks, only merges are left, and merges stay human. The founder asked earlier for human steering to shrink over time.
- *Settled:* **optional, off by default** (`trust: true` in config). It stays for teams that want bug and task merges to earn auto-approval; `neverTrust` still holds for feature merges and every release.

**C3. Outcome follow-up.** The SRE and agentic AI want it optional; the product owner wants it on the full lane.
- *Settled:* **on for the full lane, off for light**, and `Metric: None, because ...` is allowed.

**C4. Data work.** The architect wants an additive table in the light lane; the project manager and SRE want data in the full lane with the DBA.
- *Settled:* a migration that **alters or drops** existing columns or tables runs in the full lane with the DBA. An **additive** migration runs in the light lane, with a down migration and the DBA as a required CODEOWNER on the PR.

**C5. Record gate 5 from the GitHub approval instead of `sdlc approve 5`?** The tech lead wants one approval, not two.
- *Settled:* **not yet.** It needs the GitHub API in the hooks, and a typed approval is the guarantee that has been tested. Revisit after the cuts land. `approve` does advance by itself.

**C6. Review ledger rules.** The tech lead says `fixed: <sha>` touching the exact file, the H/F id rules and the stale-packet refusal will be fought by developers.
- *Settled:* `request` **rebuilds a stale packet** instead of refusing; the `fixed: <sha>` file rule applies only when the pre-review says `Risk: high`.

**C7. Automatic retro triggers.** The project manager wants them cut.
- *Settled:* the trigger stays, shown in `status` only; it is no longer added to session start.

## Optional steps (off by default, switched on per repo, per feature or by risk)

Design stage and board (data alter/drop, high-risk paths, a new component, or `--design`), C4 changes (a new container), screens and accessibility (UI changes), facts.md (brownfield and data), ER diagram (advice only), OpenAPI (API kind; only breaking changes are checked), `gateRepeats` and `dataCheckCommand`, the QA verdict (Risk: high), lenses beyond correctness, simplicity and tests, outcome follow-up on light, freeze, earned trust, metrics, retro, evals.

## Cuts

- PRD sections Evidence, Goals and non-goals, Proposed lane; Stakeholders, Dependencies and Release criteria become optional (product owner).
- pr.md sections Mutations, Defects, Security results, Tasks, Review honesty (tech lead, QA). Kept: Summary, Test results, Pre-review, Not verified.
- release.md required sections Artefact, Cost delta, Runbook, Traps added; they stay in the template as prompts (SRE).
- The design-review board template, the three-discipline minimum and the ADR "downside" keyword check; the review questions live in the ADR's `## Review` (architect).
- The `greenfield` kind (one heading).
- `skills/ai-sdlc/` (an older cycle that competes with `org-ai-sdlc`); its standards move into the repo kit (agentic AI).
- Agents merged, 21 to 14: agentic AI with AI agents, SRE with ops, QA with SDET, project manager into CTO, C4 into architect; Confluence and GitHub experts removed.
- Commands merged, 18 to 14: kickoff into start, plan with analyze, design with design-review, build with tests.
- PostToolUse audit on every tool call (a node process per call); audit decisions only, on edit tools (SRE, agentic AI).
- The banned-text check moves from the stop hook to the house-style lint; the secret scan stays (SRE).
- The mod's own copies of SLA and never-trust tables; it reads them from `lib.mjs` (agentic AI).

## The default path

**A feature (light lane):**
1. `/ai-sdlc:start <idea>`: triage picks the lane; the product owner asks its questions.
2. Answer them, then approve the spec: a short PRD (Problem, Users, Questions, Assumptions, Requirements, Never, Out of scope, Outcome metric, Open questions) plus `acceptance.feature`. One approval.
3. `/ai-sdlc:build <f>`: tests first, then code; the gate and retries run on their own and Build passes on checks.
4. `/ai-sdlc:verify <f>`: gate, proof, packet, pre-review, PR.
5. A CODEOWNER reviews from "Look here first" and the human types `sdlc approve <f> 5`.
6. A human merges and deploys.
7. `/ai-sdlc:release <f>`: tested rollback and probe results; the human approves.

Three human waits instead of five.

**A bug:** unchanged, except the repro is proved on the base code.

## Overruled or deferred

- Recording gate 5 from the GitHub approval (C5): deferred.
- Cutting the postmortem deadline (SRE, optional): kept, because it is the one learning loop that runs under pressure (project manager).
- Cutting earned trust outright (project manager): made optional instead (C2).

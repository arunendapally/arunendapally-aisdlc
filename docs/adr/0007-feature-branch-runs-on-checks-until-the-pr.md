# ADR-0007: Plan and Design pass on checks on the feature's own branch; the PR review stays the human gate

Status: proposed
Date: 2026-11-06

## Context

Only Build passes on checks in every lane (scripts/lib.mjs:28-30, F1); Plan and Design wait for a named person. The one way around those waits is repo-wide autonomy (scripts/lib.mjs:435, F4), which also lets the agent push the reviewed commit to main (scripts/sdlc.mjs:573-583, F5), taking away the PR review. The 2026-11-05 dogfood run stopped 4 times before any PR existed (PRD Problem). Feature work always ends in a PR a person merges, since agents cannot push to main (F6). R1 and R2 need gates 1 and 3 to pass on checks on a branch; R3 and R7 need Verify and Release to keep their people. ADR-0005 decided that every merge needs a person and that an approval covers what was checked; this ADR keeps both and changes no decision in it.

## Options

- **Gates 1 and 3 pass on checks when requested on the feature's own branch, unless the repo names a person for that gate or the change is risky:** a fixed list of two stages. Might win: one small rule, no new switch; the existing gateOwners setting, which agents cannot write (scripts/hooks/pre-tool.mjs:231), is the per-repo off switch. Might lose: a weak spec is first read by a person at the PR, after Build.
- **A repo-level key in .ai-sdlc/config.json, set once:** the same effect, opt-in per repo. Might win: explicit. Might lose: a second setting that means "who decides gate N", next to gateOwners, which already says it.
- **A per-feature autonomy flag a person sets at init:** opt-in per feature. Might lose: one more human step before every feature, the stop the owner asked to remove (PRD Q2).
- **Keep repo-wide autonomy as the only route:** Might win: nothing to build. Might lose: it also merges to main with no PR review (F5), which the owner ruled out (PRD Constraints).

## Decision

Gates 1 and 3 pass on checks when requested on the feature's own branch, unless the repo names a person for that gate or the change is risky.

- The stages are listed once, as BRANCH_AUTO = [1, 3] in scripts/lib.mjs. Verify (5) and Release (6) are never in it, and a test fails if any BRANCH_AUTO stage appears in neverTrust for any lane.
- A gate passes on checks this way only when all of these hold: state.branch is set and is not a protected branch; git rev-parse --abbrev-ref HEAD equals state.branch exactly and is neither "HEAD" (detached) nor "" (git failed); the gate has no record yet at this stage, so a waiting or rejected gate keeps its person; .ai-sdlc/audit.jsonl holds no "reject" event for this feature and stage, so a person's send-back keeps its person after drift clears the gate record (scripts/sdlc.mjs:315); gateOwners lists no name for the stage; the error budget is not frozen; and, for gate 3, the feature is not kind data and its PRD's Security and privacy line is not risky (nonFunctionalProblems().risky).
- When any condition fails, the gate waits for its person as today, and the message names the condition that kept the person; on a checkout other than state.branch it says "switch to <branch> and request again to pass on checks". A feature made before createFeature set state.branch (scripts/lib.mjs:422) waits for its person as today.
- The gate is recorded by "checks: feature branch" with its fingerprint, so drift still sends the work back. Where more than one route applies, the label is the first of: "autonomy granted by <name>", "earned trust", "feature branch".
- Every pass on checks is written to .ai-sdlc/audit.jsonl as event "auto" with feature, stage, revision and by.
- The review packet lists, from audit.jsonl, every pass on checks for the feature with its time and revision, and every spec-drift and plan-drift event, so a spec or design revised during Build and passed again is shown. A second pass still needs "## Changes since vN" in the document (scripts/sdlc.mjs:327-331).
- On the branch, a drift message says "Request gate N again: it passes on its checks on this branch", not "so a person approves".
- The PR size check runs on these passes as on any automatic gate (scripts/sdlc.mjs:422).
- The intent question stays a person's answer; Plan cannot pass without it.
- Moving a light feature to the full lane stays a person's step unless repo autonomy is on, as today.
- ADR-0005 stays accepted; nothing in it is superseded.

Confirmed by: tests/branch-autonomy.test.mjs, which fails if gate 5 or 6 passes on checks; if gate 1 passes on main, detached HEAD, or with gateOwners naming a person; if a rejected or waiting gate is overwritten; if a gate a person rejected passes on checks after a PRD edit drifts the feature back; if gate 3 passes for kind data; if a frozen budget passes a gate; or if an automatic pass leaves no audit line.

## Consequences

- Good: an ordinary feature runs from intent to PR with no person in between, and the PR is the one review.
- Good: no new switch; a repo that wants a person at Plan or Design names them in gateOwners.
- Downside: Plan and Design are no longer read by a person before Build; a wrong spec costs a Build before it is caught.
- Downside: data work, a risky Security and privacy line, and the light-to-full lane move keep their person, so those features still stop before the PR.
- Downside: a branch already over the lane's code limit is refused at Plan or Design where a person's approval would not be.
- Downside: an escaped bug resets the full:1 and full:3 streaks even for gates passed on checks (scripts/sdlc.mjs:52-64). This only tightens, so it stays.
- Downside: once a person sends back gate 1 or 3, that stage keeps a person for the rest of the feature, even after the rework they asked for.
- Risk: a gate left waiting from before this ships, then cleared by drift, re-passes on checks. It is a one-time case; a send-back is the decision this rule keeps.
- Risk: state.branch is named by the agent at init, so any non-protected branch qualifies, a shared integration branch included. Work there still reaches main only through a PR; a repo that wants a person there lists the branch in protectedBranches.
- Risk: PRs that a Plan or Design person would have stopped reach review. Revisit if the owner sends back a PR for a spec or design reason (the intent's "Drop if"), counted as gate 5 reject events in audit.jsonl on features with an "auto" event at gate 1 or 3, with the reason read by Arun for the first three PRs (PRD A1).

## Review

- Q1 (design-review): The runner-up was argued as per-feature opt-in at init, which adds a stop per feature. Why not a repo-level key in .ai-sdlc/config.json (agents cannot write it, scripts/hooks/pre-tool.mjs:231), set once per repo? As written, BRANCH_AUTO also silently overrides a repo's gateOwners for stages 1 and 3 (scripts/lib.mjs:124): should a named gate owner keep that gate? A: Partly. A new key would be a second way to say who decides a gate; gateOwners already says it and agents cannot write it, so a named owner keeps the gate and an empty list means checks on the branch. Changed: Options adds the repo key; Decision adds the gateOwners condition.
- Q2 (design-review): The PRD Constraints say "ADR-0005 is superseded by this feature's design (CTO triage)"; the ADR says ADR-0005 stays accepted. Which is right, and what in ADR-0005 does this ADR actually change? A: The ADR. ADR-0005 decides merges, fingerprints, risk tiers, revert lines and close; this design keeps all of them and reuses the fingerprint, so nothing is superseded and the PRD line is wrong. Changed: Context and Decision say no ADR-0005 decision changes; the PRD line needs the CTO (Open).
- Q3 (design-review): A PRD edited during Build drifts back to stage 1 (scripts/sdlc.mjs:307-320), then gates 1 and 3 re-pass on checks on the branch with no person, so R4's send-back reaches no one before the PR. Should the packet show each spec or design revision passed on checks (state.revisions, the drift audit events), and does next() at sdlc.mjs:304 still say "so a person approves" on a branch? A: Accepted. The PR reviewer is who the send-back reaches, so the packet lists each automatic pass with its revision and each drift event, and the re-pass still needs "## Changes since vN"; next() gets a branch wording. Changed: Decision (packet, next() wording).
- Q4 (security): state.branch is whatever the agent passed to "sdlc init --branch" (sdlc.mjs:249, init is not a human verb), so "the feature's own branch" reduces to "any non-protected branch", including a shared integration branch. And git rev-parse --abbrev-ref HEAD returns "HEAD" when detached and "" when git fails (lib.mjs:202-207). What exactly does the rule compare, and what stops those values matching? A: Partly. It compares HEAD's name to state.branch exactly and now rejects "HEAD", "" and protected names on either side. Any non-protected branch is accepted on purpose: it still ends in a PR, and a repo protects a shared branch via protectedBranches. Changed: Decision states the comparison; Consequences states the residual risk.
- Q5 (security): The auto path records by "checks: ${spec.owner}" (sdlc.mjs:510), which for gate 3 reads "checks: architect + product lead" or "+ DBA", naming people. The escape demotion only tightens, so it stays. Changed: Decision (label, precedence, test); Consequences (escape downside).
- Q6 (security): sdlc.mjs:500 refuses only an already approved gate. - Q7 (security/dba): For kind data, stage 3 has a DBA owner (lib.mjs:66), and a light feature whose NFR touches security is moved to the full lane (sdlc.mjs:379-386, today only under autonomy; otherwise it adds a "ask a human to type sdlc lane full" stop).

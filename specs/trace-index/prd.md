# PRD: trace-index

Capability: gates-and-names (specs/gates-and-names/slices.md)

## Intent

- Change: A requirements index that traces back: from each requirement to its scenarios, tests, ADRs and decisions, and from a test, ADR or decision back to the requirement
- Smallest: One command prints the index for a capability, both ways, generated from what the files already say
- Drop if: Nobody opens it, because the per-feature test matrix already answers the questions people ask

## Problem

The trace from a scenario to its tests exists one feature at a time (F1), and decisions name the requirements they change (F2), but nothing shows a capability's requirements together, or answers "which requirement is this test or ADR or decision for?" (facts Not found). Arun asked whether a requirements index that traces back should exist; the agreed answer was yes, generated by the tool and never kept by hand, named by feature and requirement so no new id scheme is needed (Arun, plugin owner, 2026-11-06).

## Users and jobs

- Product owner: when I look at a capability, I want every requirement with its scenarios, tests and decisions in one view, so I see what is covered and what changed.
- Reviewer or tech lead: when I look at a test, ADR or decision, I want to find the requirement it serves, so I can judge it against the need.

## Questions asked

- Q1: Should there be a requirements index which traces back? A: Arun asked it; the answer he took was yes, generated, never hand-kept, with requirements named by feature (for example branch-autonomy/R3). (Arun, plugin owner, 2026-11-06)

## Current system

Per-feature scenario-to-test trace (F1); decision rows name the features and requirements they change (F2); a capability lists its features (F3).

## Assumptions

- A1: An ADR traces to a requirement when the ADR names it as "<feature>/R<n>" or names the feature's R id in its Context. [unconfirmed]
- A2: The index is printed on demand and written nowhere, so it can never drift. [unconfirmed]

## Requirements

- R1. (must) A person can see, for a capability, each requirement named by feature with its scenarios and the tests that prove them. Needs: each feature's requirements, scenarios and tests (F1, F3).
- R2. (must) The same view lists, for each requirement, the decisions that changed it and the ADRs that name it. Needs: decision rows (F2) and ADR text.
- R3. (must) A person can look up a test file, ADR or decision and see the requirements it traces to. Needs: the same links read backwards.
- R4. (must) A requirement with no scenario or no test is marked so in the index. Needs: nothing new.

## Non-functional requirements

- Performance: None, because it reads the specs and tests of one capability on demand.
- Security and privacy: None, because it only reads repo files.
- Accessibility: None, because it is command output.
- Limits and quotas: None, because no new input or call is added.

## Never

- Never write the index into a file that people then keep by hand.

## Out of scope

- Superseding requirements of an original feature from a change request: a later slice.
